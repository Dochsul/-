# Архитектура AINA Évidence

## 1. Оценка исходной архитектуры

Исходный сайт — один статический `index.html`. Для витрины этого достаточно, но **для электронной коммерции недостаточно**:

- нет места для хранения заявок и заказов;
- нет безопасного способа принять подтверждение оплаты (webhook) и выдать файл только после оплаты;
- статический хостинг не может хранить секреты (ключи платёжных систем).

Поэтому модернизация минимальная: **статический сайт остаётся статическим**, а коммерческая часть добавляется как небольшой сервер на Node.js.

## 2. Целевая схема

```
Браузер ──► Статический сайт (dist/: 3 языка, SEO, каталог в JSON)
   │
   └──► API сервер (server/, Node.js, без внешних зависимостей)
          ├─ POST /api/leads              заявки (минимум данных), подтверждение только после записи в БД
          ├─ POST /api/checkout           заказ + страница оплаты Revolut (только если оплата включена)
          ├─ POST /api/webhooks/revolut   подтверждение оплаты: подпись, затем сверка заказа в Revolut API
          ├─ POST /api/webhooks/stripe    запасной модуль Stripe (отключён по умолчанию)
          ├─ GET  /api/download/:token    выдача файла по одноразовому/ограниченному токену
          ├─ SQLite (data/app.db)         заявки, заказы, токены, очередь писем
          └─ private/products/*.pdf       файлы гайдов, не доступны по прямой ссылке
```

Хранение: SQLite встроен в Node 22 (`node:sqlite`), файл `data/app.db` не попадает в git. Для роста нагрузки путь миграции — PostgreSQL; слой доступа к данным изолирован в `server/db.mjs`.

## 3. Размещение

Подробное сравнение бесплатных и платных вариантов (Cloudflare, Supabase, Vercel, Render, Fly.io, VPS), ограничения коммерческого использования и расходы — в **`docs/HOSTING.md`**. Вывод: ни один бесплатный тариф не даёт одновременно постоянную базу, закрытое хранилище файлов, постоянно работающий приём подтверждений оплаты и разрешённое коммерческое использование. **Рекомендуется один маленький VPS в ЕС**; всё остальное (внешняя копия, почта, сертификат) укладывается в бесплатные лимиты. Развёртывание: `docs/DEPLOY.md`, резервные копии: `docs/BACKUP.md`. Ничего не куплено и не подключено без вашего разрешения.

## 4. Конфигурация и секреты

- Все секреты — только в переменных окружения сервера (`.env` вне git). В репозиторий попадают только `.env.example` без значений.
- Публичные данные бизнеса — `src/config/business.mjs`. Неизвестные поля = `null`.
- Сборка для продакшена (`npm run build:prod`) падает, пока не заполнены обязательные поля. Это защита от публикации незавершённого сайта.

## 5. Платежи

Подробно в `docs/PAYMENTS.md`. Кратко:

- **Revolut Merchant API** — основной провайдер (ноябрь 2026). Сервер создаёт заказ с точной суммой, клиент платит на странице Revolut, выдача файлов — только после проверки заказа через API Revolut. Существующая ссылка `pay/…` для автоматической выдачи не используется (см. `docs/REVOLUT.md`).
- **Stripe** — запасной модуль, отключён. Регистрация не нужна; включается только `PAYMENT_PROVIDER=stripe` и наличием ключей.
- **Банковский перевод** — ручная сверка, для консультаций и крупных заказов (реквизиты — владелец, ещё не подключено).

Все провайдеры выключены по умолчанию. Реальный Revolut: сначала песочница (`REVOLUT_ENV=sandbox`), боевой режим только с `LIVE_PAYMENTS_APPROVED=owner-approved` и вашим разрешением.

## 6. Безопасность (принципы)

- Цены и суммы вычисляются **только на сервере** по каталогу; клиентским ценам не доверяем.
- Заказ переходит в «оплачен» **только** после того, как сервер сам получил заказ из Revolut API и сверил состояние, сумму, валюту и номер. Подпись webhook (`v1=` HMAC-SHA256, допуск 5 минут) и защита от повторов — отдельный барьер; тело webhook доказательством не считается.
- Файлы выдаются по токену: в БД хранится только SHA-256 токена, срок 7 дней, до 5 скачиваний, ответ `Cache-Control: no-store`.
- Заявки: минимум полей, honeypot, лимит размера, rate limit по IP, экранирование вывода, запрет медицинских данных в свободном тексте (поле ограничено по длине, в UI — предупреждение).
- Заголовки безопасности: CSP, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'` (на сервере).

## 7. Санкции и клиенты из России

Коммерческий сайт не должен обходить ограничения. Реализовано:

- список `blockedCountries` в конфигурации; оформление заказа для таких стран отключено;
- если страна выяснилась уже после оплаты (через данные Revolut), заказ переводится в статус «проверка» и файл не выдаётся; возврат выполняется вручную через Revolut и фиксируется `npm run refund:record`;
- **юридическая оценка обязательна**: список стран и правила для физических лиц из России определяет юрист по актуальным санкциям ЕС и Франции, а также политика Revolut и банка. Код не решает этот вопрос сам.

Обход (чужие аккаунты, посредники, смена страны в форме) не поддерживается и не будет реализован.

## 8. Языки и SEO

- Три версии: `/ru/`, `/fr/`, `/en/`. Одна и та же структура страниц, тексты из `src/content/<lang>.mjs`. Отсутствующий ключ в одном языке ломает сборку (проверка паритета).
- `hreflang` на каждой странице (включая `x-default` → `/en/`), общий `sitemap.xml` с альтернативами.
- Open Graph и Twitter-карточки, canonical, JSON-LD: `Organization`/`ProfessionalService`, `Person` (владелец), `Product`/`Offer` только для опубликованных товаров, `FAQPage`, `BreadcrumbList`.

## 9. Тесты и CI

- `tests/*.test.mjs` — `node --test` без зависимостей: подпись Stripe, токены загрузки, валидация заявок, расчёт заказа, санкционная проверка, защита путей, паритет переводов.
- `scripts/check.mjs` — статические проверки собранного сайта (ссылки, якоря, hreflang, sitemap, CSP).
- `scripts/smoke.cjs` — браузерная проверка (Playwright, по желанию).
- GitHub Actions: сборка, тесты, статические проверки. Деплоя в CI нет — публикация только по вашей команде.

## 10. Связка с Tilda

Основной сайт собирается в Tilda. Этот репозиторий даёт Tilda:
- тексты, SEO и head-сниппеты (`tilda/pages/`, `tilda/seo.csv`);
- T123-блоки (`tilda/components/`), которые обращаются к API по CORS (`ALLOWED_ORIGINS`);
- API для оплаты и выдачи PDF. Покупатель после оплаты возвращается на страницу Tilda (`CHECKOUT_SUCCESS_URL`).

Платные PDF не размещаются в Tilda: файлы Tilda доступны по постоянным публичным ссылкам. Подробно: `TILDA_HANDOFF.md`, разделы 5–7.
