# Резервное копирование и восстановление

## Что и как копируется

- **Что:** база данных `app.db` (заказы, платежи, возвраты, токены скачивания, заявки, очередь писем). PDF-файлы в копию **не входят**: оригиналы лежат в вашей библиотеке, а на сервере их можно перезалить и сверить по SHA-256 (`node scripts/verify-files.mjs`).
- **Как часто:** раз в сутки отдельным контейнером `backup` (`deploy/docker-compose.yml`).
- **Как:** снимок через онлайн-копирование SQLite (согласован, даже если сервер в этот момент пишет), проверка `PRAGMA integrity_check` **до** шифрования, сжатие, шифрование AES-256-GCM по вашему паролю.
- **Куда:** локально на сервере (хранятся последние 14 копий и по одной за каждую из последних 8 недель) и **вне сервера** в S3-совместимое хранилище. После загрузки копия скачивается обратно и сравнивается: загрузка засчитывается только если байты совпали.
- **Тревога:** если задан `BACKUP_PING_URL`, скрипт пингует сервис мониторинга после удачной копии и `.../fail` после неудачной. Если пинги прекратились, сервис мониторинга пришлёт предупреждение.

## Очень важно: пароль

Копии содержат персональные данные покупателей, поэтому зашифрованы. **Если вы потеряете `BACKUP_PASSPHRASE`, копии прочитать нельзя, и никто, включая меня, не сможет их восстановить.** Сохраните пароль в менеджере паролей отдельно от сервера. Пароль не короче 20 символов.

## Ручная копия
```bash
docker compose -f deploy/docker-compose.yml run --rm backup node scripts/backup.mjs
```

## Восстановление (после потери базы)
1. **Остановите API:** `docker compose -f deploy/docker-compose.yml stop api backup`.
2. Проверьте копию, ничего не устанавливая:
   ```bash
   docker compose -f deploy/docker-compose.yml run --rm backup node scripts/restore.mjs s3-latest --verify-only
   ```
   Должно быть `verified ...` и число строк по таблицам. Ошибка `wrong_passphrase_or_corrupted_backup` означает неверный пароль или повреждённый файл.
3. Восстановите: `... node scripts/restore.mjs s3-latest` (или `latest` для самой свежей локальной копии, либо путь к файлу). Если база уже существует, скрипт откажется без `--force`, а с `--force` сохранит прежнюю как `app.db.pre-restore-<время>`.
4. Запустите: `docker compose -f deploy/docker-compose.yml up -d`.
5. Проверьте: `curl https://api.<домен>/api/health` и откройте одну из недавних ссылок скачивания.

## Что проверено автоматически
Тесты `tests/backup.test.mjs` (9 проверок) и `tests/deploy.test.mjs`:
- шифрование: неверный пароль, подмена байта, посторонний файл отклоняются; открытый текст в файле не виден;
- снимок живой базы согласован; восстановление возвращает все строки;
- восстановление не перезаписывает молча и сохраняет прежнюю базу; повреждённая или пустая база не устанавливается;
- политика хранения;
- подпись SigV4 сверена с официальным примером AWS; внешнее хранилище отклоняет неверный секрет;
- **учения:** база потеряна, копия скачана из внешнего хранилища, восстановлена, купленная ссылка снова работает; неверный пароль ничего не устанавливает;
- пинг мониторинга при успехе и при ошибке.

## Что не проверено
- Работа против настоящего Backblaze B2 / Cloudflare R2 (проверено на S3-совместимом сервере-заглушке с проверкой подписи; совпадение с эталоном AWS подтверждено).
- Запуск контейнера `backup` на реальном сервере.
- Срок хранения на стороне хранилища: настройте жизненный цикл бакета (например, удалять копии старше 90 дней), код удаляет только локальные копии.
- Регулярное учебное восстановление: рекомендую раз в квартал выполнять шаг 2 (`--verify-only`).

## Выбрано: Backblaze B2 (ноябрь 2026)

- Бакет закрытый (Private), регион EU; ключ приложения ограничен этим бакетом. Пошагово — `docs/LAUNCH.md`, раздел 8.
- `BACKUP_PASSPHRASE` (не короче 20 символов) хранится в менеджере паролей. Потеря пароля = потеря копий.
- Проверка восстановления без записи в рабочую базу: `node scripts/restore.mjs s3-latest --verify-only`.
- Зашифрованная копия самого `registration.json`: `node scripts/registration-seal.mjs seal` (тот же формат шифрования, пароль отдельный). Хранить вне GitHub.
